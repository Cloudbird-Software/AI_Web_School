一、对你产品愿景的架构评估
你的目标链路是：知识穷尽 → 无限出题 → 按人类最佳实践组卷 → 作答回流看知识点漏洞 → 定向练习测量 的数据飞轮。从代码看，架构骨架非常扎实，比绝大多数国内教育项目工程化程度高一档：

你的设想	架构对应物	落地评估
知识有限可穷尽	kp_node / kp_edge / kp_closure 知识图谱闭包表	设计到位，closure 物化加速查询
无限批量出题	instantiation/engine 确定性实例化 + 内容寻址 id（D3）	关键缺陷：学科函数库 19 个函数从未注入求值器，所有母题被迫只用 BinOp，"无限"退化为"加减乘除的有限扰动"
按最佳实践组卷	assembly 双向细目表 + CP-SAT 求解 + 启发式 + 曝光互斥	求解器纪律好（不可行必抛冲突报告），但 session 流完全不写曝光账本，"防重复"在线上失效
看知识点漏洞	report/aggregator + review/scheduler + error_type 归因	单学生维度做对了（D8 不排名合规），但 A4 追溯码在 API 出口断裂，客户端无法做 placement 关联
定向练习测量	D5 参数分场景（practice/diagnosis/measurement）	D5 在组卷侧未落地：assembly 仍读 lineage 先验而非 item_param，三场景共用同一先验值
飞轮的"动力源"问题：D6「估计器可替换 / 历史报告引用当时版本」对 AI 评分链路未闭环——scoring_trace 不记录 LLM model_version，十年后无法回放"当时是哪个模型给的 80 分"。这是飞轮长期可信度的隐患。

最严重的系统性问题不是某个 bug，而是"宪法说有、代码说没有"的虚假强制层：D1/D2 在文档里反复声称"由 DB 触发器物理强制"，但内容版本账（item_version/material_version/corpus_version）和 gate_certificate 的 FK 完全没有 DB 强制。这意味着绕过校验门直写 published 行的"宪法红线"在数据库层是裸的，仅靠应用层纪律。

八、总体评价
这是一份工程化程度明显高于一般国内教育项目的代码库：宪法 + 任务卡 + OPC 工作流 + 三本账 + 校验门 + 内容寻址 + 学科包隔离的设计骨架是严肃的，注释里大量"为什么这样写"的决策记录远超行业平均。2551 个测试的覆盖面也很可观。

但当前最大的系统性风险不是"某个 bug"，而是"宪法说有、代码说没有"的虚假强制层：D1/D2 在文档里反复声称"由 DB 触发器物理强制"，实际内容版本账三表与 gate_certificate FK 是裸的；cert:none 占位行依赖测试 fixture 预插而生产未落地；record_call 在评分链路完全不调用却声称"台账由 ai_call 内部记录"；check_consent 实现完整却无业务调用方；migrate-check 名义验证可逆实际只验证最新一个；P4 声称"30 抽样端到端"实际只有 1 个。这些都是"测试通过但承诺未兑现"的典型——而你的宪法 P3"机器信号唯一事实"恰恰想防范这种"自评汇报不算数"，这次轮到测试套件本身不够深。建议优先补齐这层"承诺兑现度"的缺口，再处理产品能力（学科函数库注入、D5/D6 闭环）与并发幂等等数据正确性问题。

全面代码审阅报告
一、总体评价
架构设计水平很高。宪法驱动开发（SDD）、三本账只增不改、校验门文化、学科中立 by construction 这些理念在代码中得到了较好的贯彻。模块边界清晰，核心域确实做到了零学科特判。以下按严重程度递减列出具体问题。

二、安全问题（Critical）
2.1 全部 API 端点无认证/授权
可复现：直接 curl http://localhost:8000/sessions 即可创建会话，无需任何 token。

main.py 没有挂载任何认证中间件
session.py POST /sessions 直接接受客户端传入的 student_alias_id，任何学生可以冒充任何其他学生创建会话、提交作答、查看弱项报告
report.py GET /reports/weakness/{student_alias_id} 同理，任何人可以查看任何学生的弱项
items.py 所有只读端点也无认证
影响：这是部署到生产环境前必须解决的 P0 问题。违反宪法 D7（PII 隔离）的精神——虽然主库只有 alias_id，但 alias_id 本身就是可被枚举的标识。

2.2 无速率限制
所有端点无 rate limiting。攻击者可以：

暴力枚举 item_version_id（虽然是 sha256，但可以探测）
对 POST /sessions/{id}/responses 高频提交，制造大量 response_event
耗尽数据库连接池
2.3 无 CORS 配置
main.py create_app() 没有添加 CORSMiddleware。如果前端在不同域名，浏览器会阻止请求；如果随便什么域名都能调 API，等于无防护。

三、数据完整性/并发问题（High）
3.1 会话服务的竞态条件
session/service.py submit_answer 是经典的 read-modify-write 模式，但没有乐观锁或行级锁：


Python

# L571: 读
session = await _load_session(db, session_id)
# L629-648: 改
session.answered_count += 1
session.current_index += 1
session.wrong_marks = marks
# L667: 写
await db.commit()
如果同一 session 的两个请求并发（网络重试、学生双击提交），current_index 可能被错误地递增两次，wrong_marks 可能被覆盖（last-write-wins）。

同样，get_next_item 中 L465 session.wrong_marks = marks 也有同样问题。

修复建议：使用 SELECT ... FOR UPDATE 或乐观锁（version column）。

3.2 practice_session 不在三本账保护范围内
session/models.py L49-117 的 practice_session 表允许 UPDATE。虽然注释说明它是"运行态"表，但 item_sequence、wrong_marks 等关键字段被原地修改。如果这些字段被错误修改，没有审计轨迹可以回溯。

建议：至少对 item_sequence 和 wrong_marks 的变更做 append-only 日志（或改用 JSONB 版本化）。

3.3 record_event 的 commit 时机问题
events/writer.py L128 await session.commit() 在 record_event 内部直接 commit。但调用方 scoring/service.py 的 score_and_record 也在 submit_answer 的上下文中被调用，而 submit_answer 在 L667 也有 await db.commit()。

这意味着一个 submit_answer 调用会产生两次 commit：一次在 record_event 内部（response_event 落账），一次在 submit_answer 末尾（session 状态更新）。如果第二次 commit 失败，response_event 已经写入但 session 状态未更新，导致数据不一致。

修复建议：record_event 不应自行 commit，应由最外层调用方统一 commit。

四、API 设计问题（Medium-High）
4.1 read_next_item 返回类型不安全
session.py L204 返回 dict[str, Any]，L211 返回 {"done": True, "session_id": str(session_id)}，L212 返回 item.model_dump(mode="json")。两种完全不同的响应结构共用一个 dict[str, Any] 返回类型，客户端无法从 OpenAPI schema 推断响应结构。

建议：定义联合响应模型或使用 response_model 的 responses 参数区分 200（done）vs 200（next item）。

4.2 无 API 版本前缀
URL 路径是 /items/...、/sessions/...，没有 /v1/ 前缀。未来做不兼容变更时无法并行部署 v2。

4.3 无分页
GET /review/due/{student_alias_id} 有 limit 参数但无 cursor/offset 分页
如果学生有 1000 条到期复习条目，只能拿到前 100 条，无法翻页
4.4 异常映射过于宽泛
session.py L128 isinstance(e, (UnpublishedItemError, ValueError)) 把所有 ValueError 都映射为 422。但 ValueError 是 Python 标准异常，很多内部 bug 也会抛 ValueError（如类型转换失败），这些应该返回 500 而非 422。

session/service.py L414-418 用 hashlib.sha256 生成种子字符串后传给 random.Random(seed)。但 random.Random 接受字符串种子时内部会做哈希处理，不同 Python 版本的实现可能不同（CPython 的 random 模块在 3.x 版本间有变更）。如果需要跨进程/跨版本确定性，应直接使用整数种子：random.Random(int(seed[:8], 16))。

7.5 ELO 模块缺少遗忘衰减

7.6 score_and_record 的 scene 类型安全
scoring/service.py L620 有 # type: ignore[arg-type] 注释，说明 session.scene 的类型（str）与 Scene（Literal["practice", "diagnosis", "measurement"]）不匹配。这个 type: ignore 掩盖了真实的类型安全问题——如果 session.scene 被设为非法值（如 "test"），运行时不会报错。

十、整体架构评价（保留意见）
优点：

三本账 append-only 的物理强制（DB 触发器 + CHECK 约束 + 角色权限三层）是真的硬核设计——很多项目只在文档里写「不删」，这里是 DB 层做不到。
内容寻址 ID（item_version_id = sha256）与「同内容必同 id」原则（公式一/二）让数据飞轮成为可能。
学科包隔离（X6 静态扫描测试）做得很彻底——核心域真的不 import 学科包。
PII vault 独立 schema 配合列级加密，比直接放主库 + 加密字段清晰。
架构性隐患：

D2「门强制」 的物理保证有结构性漏洞（BUG-ORM1）：FK 缺失让 gate_certificate_id 成为字符串而非真引用——这是 D2 哲学的破坏。
「失败占位行」反模式（BUG-G3）：用 'cert:none' 字符串当 FK 目标，依赖迁移预插但没在迁移预插——分布式系统里的「伪节点」反模式（参考 The Daily Impossible "Fake Root"）。
审计日志与业务事务耦合（BUG-C3）：D7 的「每次读必留痕」承诺在事务回滚时静默失效——审计系统应该独立于业务事务。
AI 总线的 PII 降级策略（BUG-AI1）：宁可调少不宁可漏调（注释原话）违反 D7 的「必须剥离」硬约束——合规层的硬约束不能用「降级」绕开。
测试与实现互证掩盖（BUG-T1）：用「写假 id=digest」让错误实现通过测试——这是技术债最危险的来源，比 BUG 本身更值得警惕。
查重 SQL 用错列名（BUG-G1）：一个本应作为「防御机制」的验证器完全失效——在无限批量出题场景下，重复题会直接进入已发布池。
