# OPC · AI 原生开发组织方案
## ——SDD 范式下"一个人类 + 全 AI 军团"的开发操作系统（DevOS）

> **适用对象**：母题与知识体系平台（小学语数英全年级，架构见《工程架构设计方案 v2》）。
> **模式**：OPC（One-Person Company）——一个人类 + 全部代码由 AI agent 产出。
> **范围**：从当前状态到**"小程序发布前就绪"**的全量开发组织方案（小程序本身另行设计；其后端、教研工作台、内容、API、验收体系在本方案内全部就绪）。
> **范式**：SDD（Spec-Driven Development，规格驱动开发）——规格是唯一事实源，代码是规格的派生物。
> **日期**：2026-07-23

---

## 0. 一页结论

- **OPC 开发操作系统（DevOS）五件套**：规格库（specs/）+ 任务卡系统（tasks/）+ 四角色 agent 军团（Builder/Verifier/Judge/Scribe）+ 模型路由（基准赛+遥测）+ 现实仪表盘（CI 信号为唯一事实）。五者全部以**仓库内文件**为载体，工具无关、任何 IDE 可用。
- **人类只做三件事**：决策（写/批规格、仲裁争议）、调度（派发任务卡）、验收（跑一键验收脚本、合并绿色 PR）。人类**不做**的事：写代码、听信汇报做判断、手工回归测试、在 agent 之间传递信息（一切经仓库与任务卡异步流转）。
- **核心信任模型**：**构建者不自证**——Verifier 是独立模型、独立上下文，只看规格与机器信号；agent 的文字汇报一律视为"线索"而非"事实"；唯一事实是 CI、契约测试、黄金数据集、黄金路径四路机器信号。这是防"汇报一切顺利、实际跑不起来"的总开关（§5 九道防线）。
- **并行机制**：5 波（W0–W4）推进；波内 5–10 个 agent 并行，以"任务卡 + 模块所有权 + 契约冻结 + git worktree 隔离"保证互不踩踏；人类每天的操作收敛为 4 个固定动作（看板→派发→审信号→合并），单日可稳定吞吐 5–10 个任务卡。
- **工具栈**（经事实核验）：**Trae** 负责人机交互式攻坚（SOLO/Builder 模式、多任务窗口）；**headless CLI**（首选 Claude Code `-p`/Agent SDK；接国产模型用 OpenCode）负责脚本化并行批处理——Trae 是 GUI、不适合当自动化底座，两者互补；**LiteLLM** 做模型网关（统一 API、按 key 成本核算、故障切换）；**GitHub Actions** 做 CI（唯一事实源）；任务板用仓库内 Markdown 文件（零新工具）。
- **成本工程**：任务分 S/M/W 三级，模型分 T0/T1/T2 三梯队；用**可执行基准赛**给每个候选模型打"任务类型×通过率×单价"画像，路由表由数据生成、由遥测滚动更新——"好模型/差模型"的判定是门通过率数据，不是印象。目标：T0（最贵）token 占比 <15%，W 级任务全部下沉到免费/近免费模型。
- **内容引入**：母题/变式/知识体系/错误类型/语料全部从公共知识引入，但严守两类分界——**可直接商用源**（2022 课标作事实依据、Make Me a Hanzi 笔顺、THUOCL 词库、pypinyin、py-fsrs、py-irt、古诗文/Gutenberg 公有领域文本）与**仅方法论借鉴源**（Eedi、ASSISTments、NUCLE、CMRC——不可直接商用，只学其方法论后自研+AI 生成+教研审核）。内容引入本身也走 SDD：每种资产有"引入规格卡"，产出过同一校验门。
- **出口定义**：W4 结束时达成"小程序发布前就绪清单"（§6.6）：API 冻结、学生模拟器跑通全链路、三科首批内容入库、性能与合规达标、年度重放首演通过。

## 1. OPC 模式与 SDD 范式

### 1.1 OPC 的现实与人类的三个角色

一个人类不可能审查 AI 产出的每一行代码（一天数万行），也不可能记住全部上下文。OPC 要成立，必须把人类的稀缺注意力投到杠杆率最高的三处：

| 角色 | 职责 | 时间占比 |
|---|---|---|
| **决策者** | 撰写/批准规格（L0–L2）；仲裁 Judge 无法裁定的争议；批准契约变更与波次门禁 | ~40% |
| **调度员** | 从任务板领取就绪任务卡，派发给合适梯队的 agent；处理升级队列 | ~20% |
| **验收员** | 波次出口跑一键验收脚本、看现实仪表盘、合并全绿 PR；对失败信号按升级路径处置 | ~40% |

**人类显式不做**：写代码、读 agent 的长篇汇报并据此判断（汇报只是线索）、手工测试、在 agent 之间口头传话（一切上下文经仓库文件异步流转——这是一个人能管 10 个 agent 的关键）。

**内容审核的人力归属（关键约束）**：方案中大量"教研审核/签发/标注"（C 线语篇定稿、错误类型库、黄金标注、母题签发，首批即 1000+ 内容项）不能默认由这一个人类承担。预算与归属：①人类每日内容审核上限 1 小时（只做抽检与疑难裁决，约 20–30 项/日）；②主力 = **AI 初筛 + 规则门**（W 级模型做合规/适龄/格式初筛，规则验证器做确定性检查，人类只抽 5–10%）；③关键类目（错误类型定义、黄金标注、测量用题）外聘兼职教研按件计酬（建议每科 1 名、每周 1–2 天远程）；④若上述仍不足，**自动下调 §7.3 首批数量目标**（先保数学+语文，英语内容后移）——内容目标跟着审核产能走，而不是相反。

### 1.2 SDD：规格是唯一事实源

SDD 在本方案中的确切含义：**任何代码合入前，必须存在对应的已批准规格；规格是可执行的（含契约测试与验收脚本）；规格与代码的漂移由 CI 自动检测。** 规格分四层：

| 层 | 名称 | 内容 | 作者 | 变更门槛 |
|---|---|---|---|---|
| L0 | **架构宪法** `specs/constitution.md` | 从架构 v2 提炼的 ~20 条不可违反原则（三本账、门强制、注册表纪律、学科零特判、实例内容寻址、append-only 等） | 人类 | 仅人类，需 ADR 记录 |
| L1 | **领域契约** `specs/contracts/` | 数据模型 DDL、API OpenAPI、状态机、注册表契约、事件契约（response_event）、谱系契约 | 人类 + S 级模型起草 | 人类批准；契约测试同步更新 |
| L2 | **模块规格** `specs/modules/<module>.md` | 每个模块：职责/输入输出/依赖的契约/验收测试清单/**非目标**（明确不做什么，防镀金） | S 级模型起草、人类批准 | 人类批准 |
| L3 | **任务卡** `tasks/<wave>/<id>.md` | 最小可执行单元（见 §3.2） | Scribe 生成、人类抽检 | 随用随弃，完成后归档 |

三条推论：
1. **规格即 prompt**：任务卡引用规格文件路径而非复制内容，agent 读规格即得上下文——避免上下文在转述中腐烂。
2. **契约即测试**：每个 L1 契约配契约测试（如 OpenAPI→schema 校验、状态机→迁移测试、注册表→兼容性测试），在 CI 常绿。
3. **验收即脚本**：每个 L2/L3 的验收标准是**可执行脚本**（`make accept TASK=<id>`），不是文字描述。

### 1.3 开发总原则（八条，写入 L0 宪法）

1. **规格先行**：无规格无代码；PR 必须引用任务卡，任务卡必须引用规格。
2. **构建者不自证**：任何产物的验收由独立 Verifier（不同模型、独立上下文）执行；Builder 的自测报告仅作线索。
3. **机器信号唯一事实**：CI/契约测试/黄金数据集/黄金路径四路信号为准；与汇报矛盾时信信号。
4. **黄金路径常绿**：30 个抽样题型的端到端垂直切片（§5.4）从 W1 起建立，此后任何合入不得破坏。
5. **契约冻结**：波内冻结的接口只能追加不能修改；修改走"契约变更申请→影响面分析→人类批准"。
6. **失败升级制**：同一任务失败 2 次即升级（更强模型/更小任务/人类仲裁），禁止静默重试、禁止"绕过式完成"（删测试、改断言、注释掉失败项——CI 静态检查拦截）。
7. **一切留痕**：每个 PR 关联任务卡、模型标识、token 成本；每月成本与质量报表自动产出。
8. **小而绿**：任务卡粒度 = 单个 agent 一次会话可完成 + 可独立验收（目标 2–6 小时 agent 工时）；大任务必须先拆卡。

## 2. 工程骨架：仓库与工具链

### 2.1 Monorepo 目录结构

```

│   ├── constitution.md         # L0 架构宪法
│   ├── contracts/              # L1：db/、api/、state-machines/、registries/、events/
│   ├── modules/                # L2 模块规格
│   └── adr/                    # 架构决策记录（宪法变更留痕）
├── tasks/                      # 任务卡
│   ├── board.md                # 文件型任务板（就绪/进行/待验/完成/升级）
```

### 2.2 git 工作流与 CI（唯一事实源）

- **分支**：`main` 永远可发布（黄金路径绿）；每个任务卡一个 `task/<id>-<slug>` 分支；agent 用 `git worktree` 开独立工作目录（并行不互踩）。
- **PR 门禁**（GitHub Actions `pr-check`）：静态检查（含"绕过式完成"检测：禁止删除/修改既有测试断言、禁止新增 `@skip`）、单测、契约测试、黄金数据集回归、黄金路径（抽样 5 题快速版）。全绿 + Verifier 报告 PASS → 人类合并。
- **Nightly**：全量集成 + 黄金路径完整版（30 题）+ 历史实例重放抽样 + 成本报表。红灯即次日第一优先级。
- **标签**：`wave-exit-<n>` 标记每个波次出口（可回滚到任一出口）。

### 2.3 工具栈与分工（经事实核验，2026 年中）

| 工具 | 角色 | 说明 |
|---|---|---|
| **Trae**（现有） | 交互式攻坚：S/M 级任务、规格起草、疑难 bug 会诊 | SOLO/Builder 模式 + 多任务窗口（建议单 workspace ≤5 个并行任务）；`.trae/rules` 放角色规则；MCP 接仓库工具 |
| **Claude Code**（headless） | 脚本化并行批处理主力 | `claude -p` + Agent SDK 可编程派发子任务；官方 GitHub Action 可用；仅 Claude 模型 |
| **OpenCode**（MIT） | 接国产模型的 headless 通道 | `opencode serve` HTTP 编排 + 75 provider（经 LiteLLM 接 DeepSeek/Qwen/GLM/Kimi），W 级任务走这里 |
| **LiteLLM**（自托管） | 模型网关：统一 API、按 key 成本核算、fallback | 每个 agent 角色发独立虚拟 key → 成本天然按角色归集；开源版够用 |
| **GitHub Actions** | CI 唯一事实源 | 见 §2.2 |
| **任务板** | 仓库内 `tasks/board.md` + 目录状态 | 零新工具；人类与 agent 都直接读写 |
| 数据库/队列/存储 | 本地 docker-compose（PG16+Redis+MinIO） | 与架构 v2 选型一致 |

**为什么不全靠 Trae**：Trae 是 GUI，并行靠人工开窗口（≤5 个/工作区），无法脚本化批量派发与回收；headless CLI 进程天然可并行（tmux + worktree），配合派发脚本才能实现"人类同步启动 5–10 个 agent"。**推荐配比**：Trae 开 2–3 个窗口做高价值交互任务，headless 池跑 3–7 个批处理任务。

### 2.4 `.agent/` 目录：DevOS 的弹药库

- `roles/`：四个角色 prompt 模板（附录 B），每个模板含：角色边界、输入清单（规格路径）、输出格式（结构化报告 schema）、禁止事项（如 Verifier 禁止读 Builder 的汇报）。
- `rules/`：通用工程规则（代码风格、L0 宪法摘要、测试纪律），用脚本同步生成 `.trae/rules/*.md`、`CLAUDE.md`、`AGENTS.md`——一处维护、三处生效。
- `routing.yaml`：模型路由表（§4）。
- `telemetry/`：每次任务的门信号与成本 JSONL，仪表盘数据源。

## 3. Agent 军团：角色与并行机制

### 3.1 四角色谱系

| 角色 | 职责 | 模型梯队 | 关键纪律 |
|---|---|---|---|
| **架构师** = 人类 + S 级模型（Trae 窗口） | 规格起草与批准、契约设计、争议仲裁、波次门禁 | T0 | 宪法与契约变更必须人类落笔批准 |
| **Builder** | 按任务卡实现代码+自测，提交 PR | T1（M 级任务）/T2（W 级任务）/T0（S 级任务） | 不得修改验收测试与契约测试；失败如实报告 |
| **Verifier** | 独立于 Builder 验收：对照规格+验收脚本+代码走查（含**测试强度审查**：禁弱断言凑数），出结构化 PASS/FAIL 报告 | **梯队 ≥ Builder 梯队，且必须与 Builder 不同模型家族**（防同源盲区与能力倒挂；同家族不同代不算隔离） | 禁止读 Builder 的汇报；只看规格、diff、CI 信号 |
| **Judge** | Builder 与 Verifier 争议、CI 红但原因不明时的裁决；输出根因分析 | T0 | 只裁决不下场改代码 |
| **Scribe** | 任务卡生成与细化、规格同步、文档、遥测汇总、周报 | T2/免费档 | 纯文书，不碰业务代码 |

### 3.2 任务卡规范（SDD 的执行单元）

```yaml
# tasks/w2/T-W2-014.md
id: T-W2-014
wave: W2
title: 实例化引擎——槽位约束求解器（连续域属性采样）
spec: [specs/modules/instantiation-engine.md#3.2, specs/contracts/registries/interaction.yaml]
context_paths: [src/core/instantiation/, tests/golden/instantiation/]
deliverables: [src/core/instantiation/sampler.py, 单元测试, 黄金样例×5]
acceptance: make accept TASK=T-W2-014     # 可执行！脚本内含：单测+契约测试+黄金样例比对
model_floor: T1                           # 最低可用梯队；先试 T1，失败 2 次升 T0
token_budget: 400k
owner_module: core/instantiation          # 模块所有权：同模块同时仅一张卡在进行
depends_on: [T-W1-006]                    # 依赖冻结后可并行
non_goals: [连续域符号积分, WASM 沙箱]     # 防镀金
escalation: fail×2 → T0 重试 → Judge 会诊 → 人类
```

任务卡由 Scribe 按 L2 规格批量生成，人类抽检 20% 后批量放行。

### 3.3 并行机制：四个互不踩踏的保证

1. **模块所有权**：`owner_module` 互斥——同一目录同时只有一张任务卡活跃；任务板自动校验冲突。
2. **契约冻结**：波次启动时冻结本波涉及的全部 L1 契约；跨模块依赖只走契约 + 契约测试自带的 mock/fixture，Builder 之间零沟通也能对接。
3. **worktree 隔离**：每个 agent 一个 `git worktree` + 独立 docker-compose 项目名（端口隔离），互不干扰。
4. **波次门禁**：波内任务全部完成且出口脚本绿 → 打 tag → 才能开下一波（防地基未稳就盖楼）。
5. **关键路径与阻塞处理**：每波启动时由 Scribe 标注关键路径（被依赖最多的任务链）；被依赖卡进入升级流程时，下游卡自动冻结并改派其他就绪卡，避免整链空转；任何任务卡阻塞超 48 小时自动升级人类；同一模块排队任务超 3 张 = 该模块应拆分或补契约的信号，触发人类评审。

### 3.4 人类的一天（5–10 并发的实操）

```
早 15min   看板+仪表盘：nightly 绿否？哪些 PR 待合并？升级队列有什么？
上午       合并全绿 PR → 从就绪队列取 5–10 张任务卡 → 派发：
           · 2–3 张 S/M 级 → Trae 窗口（S 级配 T0 模型，交互式）
           · 其余 → ./tools/opc dispatch T-W2-014…（headless 池，tmux+worktree 并行）
午后       巡检信号（CI 面板，不看汇报）；处理 Verifier 报告；FAIL 的按升级路径处置
傍晚       验收+合并（合并集中在午/晚两个时段，避免全天被 PR 打断）；更新任务板；
           跑波次出口脚本（临近门禁时）；15min 成本日报
```

`opc dispatch` 脚本：读任务卡 → 查 routing.yaml 选模型 → 渲染角色 prompt（拼入规格路径）→ 起 worktree → 调 headless CLI（claude -p / opencode run）→ 写 telemetry。Verifier 在 PR 创建后由 CI 自动触发（独立模型）。

## 4. 模型路由与成本工程

### 4.1 任务分级 × 模型梯队

| 任务级 | 典型内容 | 模型梯队 | 候选（2026 年中，价格会变动） |
|---|---|---|---|
| **S**（架构/契约/疑难杂症） | L1 契约设计、跨域集成 bug、Judge 裁决、黄金路径排障 | **T0** | Claude（Sonnet/Opus 档）、GPT 高配 |
| **M**（规格明确的实现） | 模块实现、验证器插件、渲染组件、单测编写 | **T1** | DeepSeek-V/R、Qwen3-Coder、GLM 高配 |
| **W**（机械杂活） | 样板/CRUD、文档、数据格式转换、任务卡生成、fixture 制作 | **T2** | 豆包、GLM-Flash（免费档）、Qwen-Turbo、DeepSeek 缓存命中 |

**路由原则**：①任务卡标 `model_floor`（最低梯队），**先用最低可用梯队**，失败才升级——贵模型不是默认项；②Verifier 必须与 Builder 不同家族；③AI 网关（LiteLLM）按角色 key 归集成本，超预算自动降级或暂停。

### 4.2 模型基准赛（"好模型/差模型"的判定器）

不靠印象，用**可执行基准赛**给每个候选模型画像：

- **任务集**（固定 30 题，**私有仓库存储、不进主仓库**，防泄入训练语料导致基准失真；每季度轮换 1/3 题目并留轮换档案）：规格理解（读 L2 规格写出接口骨架）、代码实现（3 个真实历史任务卡）、bug 修复（埋入已知 bug 的代码）、测试编写、JSON/DDL 精确输出、长上下文检索（从规格库找矛盾）。
- **评分**：全部可执行——编译通过？测试过？diff 与参考实现的语义等价度（裁判模型须与被测模型不同家族，只用于离线基准）。
- **产出**：`routing.yaml` = 模型 × 任务类型 × 通过率 × 千 token 成本 → 按"单位通过成本"排序生成梯队。
- **频率**：新模型上市或每 2 个月重跑一次（W 级任务，成本极低）。

### 4.3 遥测动态路由

`.agent/telemetry/` 记录每次任务的（模型， 任务类型， 门信号结果， token 成本， 升级次数）。Scribe 每周汇总：某模型在某任务类型上门通过率 <60%（**最小样本量 ≥20 次**，防小样本噪声抖动路由）→ 路由表自动降权；**"哪个模型好"因此始终是当前数据，而不是三个月前的印象**。这正是 AI 产品里"任务分级路由"思想在开发侧的镜像。

### 4.4 成本纪律

单卡 token 预算硬上限（超支自动停止并升级人类）；上下文卫生（任务卡只给路径索引，agent 按需读文件，禁止把整库塞进 prompt）；LiteLLM 缓存与批处理；失败 2 次必须升级而非无限重试（重试是最贵的浪费）；月度成本报表含"单位合入 PR 成本"指标。目标：T0 token 占比 <15%。**总预算硬顶**：首程（W0–W4）开发算力预算建议设 ¥10–20 万量级（示例基线，W1 出口按实测单位成本重校准），消耗达 80% 自动告警并强制路由复核——超支时优先压缩 W 级任务外包模型档次，不动 S 级质量投入。

## 5. 防"一切顺利但跑不起来"：九道防线（本方案核心）

| # | 防线 | 机制 | 针对的失败模式 |
|---|---|---|---|
| 1 | **可执行验收先于代码** | 每张任务卡的验收脚本在派发前由 Scribe/Verifier 备好；**验收脚本自身纳入 Verifier 走查（含测试强度审查），并以 mutation 自检**（故意注入已知错误，脚本必须能抓住，防"写弱的验收"）；`make accept` 不过=任务未完成，无例外 | "代码写完了"≠"能跑" |
| 2 | **构建者不自证** | Verifier 独立模型+独立上下文，只看规格/diff/CI；PASS/FAIL 结构化报告 | 自评虚报 |
| 3 | **契约冻结+契约测试** | 跨模块只认冻结契约；契约测试 CI 常绿 | 并行开发接口撕裂、集成地狱 |
| 4 | **黄金路径常绿** | 30 个跨学科抽样题型（矩阵 spike）的端到端脚本：定义→生产→门→组卷→渲染→作答→评分→估计全链路，PR 跑 5 题快版、nightly 跑全量 | 模块各自绿、系统不绿 |
| 5 | **黄金数据集回归** | 固定输入+已知正确输出：100 母题实例化期望、N 份标注作答的期望评分、组卷约束用例（含不可行用例的期望冲突说明） | 回归悄悄发生 |
| 6 | **现实仪表盘** | 防线 #3/4/5 等机器信号的**唯一事实呈现层**：CI 状态/契约覆盖/黄金路径/测试数趋势/每晚重放；agent 汇报与之矛盾时以仪表盘为准并记录该 agent 的"虚报率" | 汇报失真无法发现 |
| 7 | **每波可运行出口** | 每波结束是人类可一键执行的 demo 脚本（`scripts/wave-exit/w2.sh`），眼见为实，不接受文档汇报 | 里程碑注水 |
| 8 | **失败升级制** | fail×2→升梯队→Judge→人类；CI 静态检查拦截"绕过式完成"（删测试/改断言/加 skip） | 静默消化失败、带病合入 |
| 9 | **Nightly 全量集成+重放** | 每晚全量集成+历史实例重放抽样+Parquet 归档演练；红灯次日置顶 | 问题晚发现、定位难 |

**问题定位保障**（呼应"问题极多又难定位"）：①全链路 trace_id（任务卡 id→PR→CI run→部署），②黄金路径每步输出中间产物快照可对比（哪一步偏离一眼可见），③契约测试失败信息含期望值/实际值 diff，④Judge 的根因分析报告模板强制"最小复现+根因+修复+防再发测试"四段式。

**反模式清单**（发现即红灯）：agent 汇报与 CI 矛盾未被处理；任务卡无验收脚本先开工；Verifier 与 Builder 同模型家族；契约测试被改弱；任务板"进行中"超过 3 天未更新；黄金路径红超过 24 小时；DDL 未经迁移工具直接改库；密钥出现在仓库/日志/prompt；任务卡超 48 小时阻塞未升级。

## 6. 波次计划：从地基到"小程序发布前就绪"

> 对齐架构 v2 的 P0–P4，按 OPC 特点重排为 5 波。每波标注：目标 / 并行流（任务卡包）/ 出口演示 / 门禁。

**工程量假设与重估闸门（必须先读）**：W0–W4 合计 16–21 周、峰值 10 agent，对应的隐含假设是 **AI 等效产能**：单 agent 日均有效吞吐 ≈0.8–1.2 张 M 级任务卡（含 Verifier 往返与失败升级损耗），全程约 1800–2600 张卡，8–10 个 agent ≈ 12–14 名工程师的产能。**此假设未经验证**，因此：①W1 出口必须按实测卡吞吐/升级率/单位成本**强制重排 W2–W4**（不允许带着假设硬冲）；②范围降级预案：若实测产能 <假设的 70%，按"数学+语文优先、英语包后移为 W5、低学段包随之后移、学段灌入压缩为仅 3–4 年级"降级，保核心闭环而非求全；③降级决策权在人类，重排结果写入 ADR。

### 6.1 W0 · 地基波（2 周，2–3 个 agent，半顺序）
- 目标：DevOS 自身建成（规格库骨架、CI 三道门禁、opc CLI、docker-compose 地基、L0 宪法+L1 首批契约），另含三项基建（见下）。
- **三项基建（防"跑不起来/难定位"的地基）**：
  - **`make bootstrap` 环境自检**：一键安装并校验 docker-compose（PG16/Redis/MinIO/无头 Chromium/SymPy 依赖），输出逐项 ✅/❌ 自检报告；非专家人类第一天的第一步。依赖全锁定（lockfile+镜像 digest），本地镜像与 CI 镜像一致，`.agent/rules` 与 CI 版本同步检查进 CI。
  - **数据库迁移纪律**：Alembic 管理全部 DDL；迁移必须可逆（ downgrade 可用）；CI 每夜演练"迁移+种子数据重灌+黄金数据集回归"——迁移破坏黄金数据即红灯；禁止手工改库。
  - **secret 管理**：全部密钥（模型 API key、LiteLLM 虚拟 key、MinIO 凭证、PII 保险库密钥）存本地 `.env`（gitignore）+ CI secrets；**禁止进仓库/日志/prompt**（CI 加泄密扫描）；每个 agent 角色经 LiteLLM 发独立虚拟 key，可随时吊销轮换；headless agent 环境只注入其角色所需最小 key 集。
- 出口演示：`make demo w0`——空骨架下跑通"创建一条题目记录→过门（占位验证器）→查询"的最小链路；`make bootstrap` 在新机器 30 分钟内自检全绿。
- 门禁：CI 三门禁运转；迁移演练绿；L0 宪法人类签字。

### 6.2 W1 · 内容底座波（3–4 周，6–8 个 agent 并行）
- 并行流：①统一内容模型 DDL+版本谱系服务 ②交互/评分双注册表+契约测试 ③校验门框架+门证书+DB 触发器 ④知识图谱底座（kp 表+closure+release）⑤语料库底座+来源登记表 ⑥黄金数据集 v1（50 真实母题，覆盖 10 交互）⑦教研工作台骨架（登录+题库 CRUD 只读）。
- 出口演示：`make demo w1`——DSL 定义 3 个母题→实例化→过门→入库→API 查到；黄金数据集回归绿。
- 门禁：**矩阵 spike 实证**（对齐架构 v2 的 P0 要求）：≥10 种交互 × 6 种评分 × 4 级生产线的抽样题型走通"定义→生产→门→组卷→渲染→作答→评分→估计"全链路（30 题全量留 W3，但**能力矩阵的每个格子在 W1 出口必须已有至少一个实证样本**）；契约测试覆盖率 100%（冻结契约全有测试）；实测卡吞吐数据产出并触发 W2–W4 重排。

### 6.3 W2 · 生产波（4–5 周，8–10 个 agent 并行）
- 并行流：①A 线实例化引擎（DSL/槽位求解/内容寻址/变式引擎）②B 线语料装配线 ③数学包（函数库/验证器/评分器/渲染组件/约束 overlay）④语文包 A 线（字词库/混淆图/拼音字库管线接入）⑤通用+数学验证器组 ⑥渲染底座（Render IR+HTML/CSS→PDF）⑦追溯码与 paper/paper_item ⑧工作台 v2（母题表单+实时预览+签发）。
- 出口演示：`make demo w2`——教研在工作台审阅签发一个数学母题→生成周更静态卷（含 QR+题码）→PDF 下载；黄金路径扩到 15 题型。
- 门禁：受控变式证书机制可用；门物理阻断有"绕过直写失败"测试；静态卷可对外（S1 后端就绪）。

### 6.4 W3 · 学科与评分波（4–5 周，8–10 个 agent 并行）
- 并行流：①C 线素材工坊+语文阅读题组 ②D 线命题工坊+作文 AI 量规四步 ③英语包（词表/音标/语法验证器）④TTS 产线+音频素材门+限次播放 ⑤组装引擎（四维编译+CP-SAT 离线+启发式在线+曝光账本）⑥评分域全量（等价/分步/关键点/错误推断）⑦S2 扫码批改后端（拍照上传→结构化评分→报告 API）⑧低学段包（注音/朗读/低段 overlay）。
- 出口演示：`make demo w3`——英语听力卷（卷面音频二维码+在线限次播放）+作文 AI 评分（影子模式）+一次完整诊断组卷（含不可行约束的冲突说明）。
- 门禁：黄金路径 30 题型全绿；置信度四层落库；英语包影子验收（核心零改动）。

### 6.5 W4 · 闭环硬化波（3–4 周，6–8 个 agent 并行）
- 并行流：①数据域（response_event 全要素+Parquet 归档+分区）②参数标定（先验/实测/收缩/分场景）+掌握度双轨 ③复习排程 v1+缺口盘点+健康度退役 ④AI 能力总线成本核算+合规层（PII 保险库/时长保护）⑤**学生模拟器**（dev-only Web：模拟在线练习/扫码/诊断全链路；定位为 **OpenAPI 的参考客户端**，其全部调用即 consumer-driven 契约测试的主体）⑥API 冻结 v1+OpenAPI 契约测试 ⑦性能与压测 ⑧年度重放首演。
- 出口演示：`make demo w4`——学生模拟器走完"领取周卷→扫码批改→在线练习→诊断→报告"全链路；重放演练报告。
- 门禁：**§6.6 就绪清单全绿**。

### 6.6 "小程序发布前就绪"清单（W4 出口定义）

1. API v1 冻结（OpenAPI），契约测试常绿；小程序团队可仅凭契约开工。
2. 学生模拟器跑通全部 C 端链路（作为 OpenAPI 参考客户端 + consumer-driven 契约测试主体，API v1 的冻结质量由其契约测试背书）；**微信端特有能力清单**（扫码入口、微信内音频播放与限次、小程序包体/组件渲染差异、微信登录）标注为"已知未验证项"，正式移交小程序设计阶段——不构成隐瞒，构成清单。
3. 内容就绪：三科首批（3–4 年级）图谱/语料/母题/素材入库量达标（见 §7.4）；周更卷三科可产。
4. 黄金路径 30 题型 + 黄金数据集 + nightly 重放全绿连续 2 周。
5. 性能达标（在线组卷 p95<2s、批改 10s 级）有压测报告。
6. 合规项机器可验部分全过（无排名查询路径/PII 不出库/时长保护触发）。
7. 运维就绪：备份恢复演练、监控告警、成本仪表盘。

## 7. 内容引入计划：公共知识 → 系统资产

> 原则：**结构与方法取自公共知识，内容本体必须原创或公有领域**。每条资产带来源登记与许可（`content/sources/` 登记），引入产物一律过校验门（含查重与适龄）。

### 7.1 四条引入管线

| 管线 | 资产 | 工艺 |
|---|---|---|
| **P-KP 知识体系** | 三科图谱种子（维度树/编码/学段标签） | 2022 课标（教育部官网全文公开，作知识点与学段要求的**事实依据**）→ AI 抽取为结构化 kp_node 草稿 → 教研审核 → 版本化入库；教材版本单元映射：教育部教材局用书目录+各版教材公开目录（只用目录结构，不复制内容） |
| **P-ET 错误类型** | 错误类型库种子（定义/判定规则/挂接 KP） | **方法论借鉴**（不可直接商用）：Eedi/NeurIPS 2020 诊断挑战（"错误选项=misconception"的四选项诊断题方法论与知识点树组织法）、数学教育 misconceptions 文献（小数/分数/退位等经典误解）→ 教研+AI 编写原创错误类型定义与原创诊断题；NUCLE/ASSISTments 同样只学方法不搬数据 |
| **P-COR 语料库** | 字库/词库/篇目库/句库/词表/音标库 | **倾向可商用、但许可须逐项法务复核后使用**（下列标注为初步检索结论，非已决事实）：Make Me a Hanzi 笔顺矢量（字体部分 Arphic Public License、衍生数据有附加条件）、pypinyin（MIT）、THUOCL 清华词库（官方许可表述模糊、商用有争议，**复核前按不可用对待**，备选：以课标字词表+自建词频统计替代）、课标附录字词表（事实依据）、py-fsrs/py-irt（MIT，排程与估计）；篇目库=公有领域古诗文原文（注意不用他人整理/注释版） |
| **P-ITEM 母题与素材** | A/B 级母题种子、C 级语篇素材 | 母题：以 75 题型矩阵为命题清单，教研+AI 按蓝图**原创撰写**（不搬运任何教辅/真题原题，外部查重门兜底）；阅读语篇：公有领域文本（古诗文、Gutenberg 英文，逐书核版权页）+AI 原创语篇（过事实核查门）；CMRC/DRCD 等学术数据仅可内部评测模型用，不入库 |

### 7.2 引入节奏与验收

- 每种资产一张**引入规格卡**（来源/许可/字段映射/抽样比例/验收脚本）；引入管线本身由 W 级模型批量执行+T1 抽检+教研审核关键类目。
- **内容生产与开发波次并行**：P-KP/P-COR 管线在 W1 启动（配合图谱/语料底座开发），P-ET/P-ITEM 在 W2 启动；内容审核产能按 §1.1 预算执行，产能不足时自动下调 §7.3 数量目标（先保数学+语文）。
- 合规红线（CI 拦截）：无来源登记不得入库；许可标注为"仅研究"的资产不得进入生产库；外部查重未过的语篇不得签发。
- 法务复核点（列入开放项，**全部"可商用源"许可逐项复核后才允许商用**）：THUOCL 许可表述、Make Me a Hanzi 衍生数据附加条件、课标引用尺度、Gutenberg 逐书版权页、"一标多本"目录数据的使用方式。

### 7.3 种子数据量目标（首批 3–4 年级）

| 资产 | 数量目标 | 说明 |
|---|---|---|

## 8. 扩展性预留

### 8.1 初高中扩展（简要）

架构的三处设计使初高中成为"加包+加注册项"而非重构：①**新学科包**：物理/化学/生物/历史/地理/道法各为一个 SubjectPack（图谱维度+语料+验证器+评分器+渲染组件+约束 overlay 六件套）；②**可预见的新注册项**：化学方程式等价评分器（符号比较扩展）、实验探究题交互（分步过程扩展）、电路图/化学装置图渲染组件、地图/图表素材类型、英语听说考试的 **ASR 口语评分器（v2 已预留接口）**、证明题（AI 量规+关键点混合）；③**测量需求升级**：初高中更接近正式测量，IRT/testlet/双向细目表（v2 已内建约束 schema）从预留转正式。知识图谱节点从千级升到万级——仍在 PG 单库论证范围内。风险点提前标记：理科复杂符号排版（KaTeX 已覆盖大部分）、实验类素材版权。

### 8.2 教辅材料定制生成（预留）

教辅（教案/大纲/重点/笔记/讲义）本质是**长文档资产**，与题目共享同一底座。预留四处：①新资产类型 **DocumentAsset**（章节树结构+KP 标注+谱系+许可），复用版本/门/渲染；②生产线框架注册 **E 线·教辅生产线**：大纲蓝图（图谱子树+学情参数）→ AI 起草章节 → 校验门（事实核查/适龄/引用正确性/查重）→ 签发；③**个性化教辅**消费数据域学情（掌握度+错误类型）作为大纲参数——"按这个学生的薄弱点生成讲义"是数据飞轮的高价值出口；④渲染复用 Render IR→PDF（教辅版式模板为新的品牌模板包）。首年不实现，但生产域注册表与资产模型已为 E 线留位。

### 附录 B：角色 prompt 模板（摘要，完整版存 `.agent/roles/`）

**Builder**："你是 Builder。只允许修改 owner_module 内文件。必读：{spec 路径}、{契约路径}。完成标准：`make accept TASK={id}` 全绿。禁止：修改任何验收/契约/黄金测试；删除或弱化既有断言；在 owner_module 外创建文件。失败时输出：已完成部分/失败点/已尝试方案/建议——禁止假装成功。"

**Verifier**："你是独立 Verifier。你**没有**也**禁止寻找** Builder 的任何汇报。输入：任务卡 {路径}、PR diff、CI 输出。逐项核对验收标准，运行验收脚本，走查 diff 中的：契约违反、宪法违反（L0 摘要附后）、测试削弱、非目标镀金。输出结构化报告：PASS/FAIL + 逐项证据（文件:行号）+ 风险残留。不得修改代码。"

**Judge**："你是 Judge。输入：Builder 报告、Verifier 报告、CI 日志。输出四段式：最小复现/根因/修复建议/防再发测试建议。只裁决，不改代码。无法裁决时列出给人类的决策选项（≤3 个，含取舍）。"

**Scribe**："你是 Scribe。按 L2 规格 {路径} 生成任务卡：粒度 2–6 小时 agent 工时、验收脚本可执行、model_floor 按 §4.1 初判、non_goals 必填。输出到 tasks/{wave}/ 并更新 board.md。"
