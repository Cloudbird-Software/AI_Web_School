## 一、为什么重排：先可信，再能力，后规模

W4 出口叫"发布前就绪"，但四份独立代码审查一致证明：**发布前就绪 ≠ 可发布**。当前系统存在三类阻塞：

1. **门与账的强制是假的**——内容表 `gate_certificate_id` 无外键、内容版本账缺 append-only 触发器 → 伪造证书即可发布，脏内容可进 serving 区；
2. **在线链路是裸的**——全 API 零认证、会话提交无幂等无行锁、事件写入自行 commit → 任何人可冒充学生写入不可回滚的作答账；
3. **合规是孤岛**——家长授权模块无调用方、PII 剥离 fail-open 且带 bypass 开关 → 未成年人数据与 LLM 调用同时踩线。

在这三类未闭合前扩张功能，写进三本账的每一条数据都可能是脏的——而三本账**只增不改**，脏数据不可回滚。这直接损伤 V2「数据飞轮是唯一不可复制资产」。故 **W5 是硬前置，不与任何新功能波并行**。

## 三、波次间依赖

```
W5-R Go+BAML 重建（硬前置，独占；ADR-0004）
  ├─→ W6 引擎解锁与飞轮加速（数学函数库 + BAML 操作员/评价者 + 共识基准集）
  │     ├─→ W7-S1..S3（学生端/账号/交付）  ← 也依赖 W5-R 认证
  │     └─→ W8-S2 自适应练习（需 W6 参数闭环）
  └─→ W7-S6 部署与运维（仅依赖 W5-R，可提前）
W6 ──→ W8-S1 内容规模化 / W8-S3 机构版
W7 ──→ W8-S4 单位经济性（需真实成本与转化数据）
```

## 四、跨波并行许可（人类派工用）

- **绝对不可并行**：W5-S1（门与账物理强制）与任何写内容/写事件的任务——迁移会改表结构与触发器。
- **可提前启动**（不必等 W5 全绿，但必须等 W5-S2 认证契约冻结）：W7-S1 学生端 UI 原型、W7-S6 部署与运维骨架。
- **可与 W6 并行**：W7-S5 埋点与漏斗（只加事件，不改引擎）。
- **必须串行**：W6-S1（函数库注入）→ W6-S4（内容规模化），前者不完成，后者产出的题只是加减乘除扰动。

## 六、任务卡与 issue 的关系

- 一条 issue = 一张任务卡 = 一个可独立验收的派工单元（宪法 P8：2–6 小时/单 agent 单会话）。
- `tasks/w<N>/ISSUES.md` 是**派工台账**（含验证方法、依赖、并行批次、owner_module 互斥关系），可直接作为 GitHub Issue 正文。
- `tasks/w<N>/T-W<N>-XXX.md` 是**执行契约**（agent 实际读取的文件，含 spec 锚点、交付物、验收标准、非目标）。
- W7/W8 当前只有 ISSUES 台账；按 P5「波内冻结」原则，在波次启动时才物化为任务卡，避免过早冻结不成熟的设计。
- 仓库原有的 10 条 GitHub Issue（#20–#30）的逐条裁决见 `tasks/LEGACY-ISSUES.md`：其中 #24/#26/#28 的有效诉求已重写为 T-W6-012 / T-W6-008 / T-W6-009，其余关闭。
